## Path boundary

Normalize Windows names using trusted kernel startup roots, not a writable user mailbox. Keep Windows spelling separate from the native UTF-8 storage name. Convert well-formed UTF-16 explicitly, preserve stored spelling and reject over-budget names without truncation. Resolve existing path components with a defined invariant case mapping; reject ambiguous native names instead of selecting an unrelated file.

Support the selected C-drive absolute, current-directory-relative and root-relative forms. Canonicalize dot components before authorization. Device/UNC/unsupported extended forms must not accidentally become native paths. The existing native volume bounds whole paths and components; the Windows adapter must report those limits honestly rather than pretend to implement arbitrary NT long paths. Native storage stays case sensitive for native apps.

Use a shared, pinned case-mapping definition for file and registry identity; do not make security depend on the host compiler locale or a running user's locale. This provides a reproducible selected profile, not a claim of identical NLS tables across every Windows version. Literal Unicode identity and case matching are distinct from Unicode normalization.

The selected data is Unicode 17.0.0 simple case folding, C/S records only. A generated arithmetic-range table stores 1,512 mappings in 3,344 read-only component bytes. Full expansion and locale-specific Turkic folds are excluded. The [source, generator and license](../../third_party/unicode/README.md) are pinned. Host checks compare every code point to the independent official data, round-trip every valid scalar through the compiled codecs, and reject malformed/truncated input and undersized output. These are supporting checks, not native Windows file qualification. [Host evidence](../../evidence/M14/3/development/unicode-host.json).

## File objects and grants

The path foundation now routes the runtime adapter through a checked kernel syscall. It snapshots the process current directory under its existing blocking lock, reads bounded UTF-16 through checked user memory, and resolves existing native components with the shared Unicode table. GetFullPathNameW/A provide lexical full-name and required-capacity results without granting file access. A separate target-leaf mode preserves requested spelling for the later rename implementation while canonicalizing parent components. Existing file sharing, persistence and registry gaps below remain open; this foundation does not close M14.3.

The compiled policy passes explicit boundary cases and 5,000 deterministic mutations, including native case ambiguity, extended paths, malformed Unicode and protected-root traversal. The original extended-separator test failure and corrected supporting result are retained in [development evidence](../../evidence/M14/3/development/path-host.json). On development build `a9544396469dda7a62b514c651db6869`, [compact installation and independent starts](../../evidence/M14/3/development/compact-path-candidate.json) and the [original supported 7-Zip lifecycle and all 106 payload hashes](../../evidence/M14/3/development/original-apps-path-candidate.json) pass. A [synthetic Windows PE probe](../../evidence/M14/3/development/path-native.json) exercises the real native syscall, Unicode/UTF-8 names, lexical traversal, required capacities and malformed/unmapped input; twenty repeated executions retain zero managed pages after initialization. Its first fixture lacked a relocation directory and was correctly refused; that observation is retained separately rather than weakening the loader. These remain development observations rather than final stage qualification.

The kernel owns live file identity, pending data/deletion, access/share rules and byte locks. Process grants own independent positions and generation-checked handles. Validate an open against every existing grant in both directions before admitting it. All processes using the same file must observe the same pending object; a separate user-mode table per process would miss conflicts and lose changes.

Reuse native COW/CRC storage for durable publication. Keep dirty data bounded and allocate it only when touched; read untouched bytes from the committed file instead of copying a whole file into RAM on open. Flush must actually commit its acknowledged state. Failed writes cannot publish a successful partial result. Document the selected delayed-write/cancellation behavior separately from Windows cache-manager or universal power-loss semantics.

Internal loader/MSI reads and writes must not become a sharing bypass. Preserve existing product-ownership rollback and original payload checks. Rename/delete must consult actual open grants and preserve live file identity where supported. Unsupported asynchronous/mapped/device semantics fail clearly. Range-lock state belongs to file grants and disappears on close/process teardown; a failed lock cannot secretly acquire or consume another owner's range.

### Implemented shared-file foundation

Development build `2813675fc610ba5cae08564ea95a1c48` replaces the legacy per-process single-writer buffer with kernel-owned file identities and sparse dirty pages. All runtime and internal loader/MSI opens participate in the same bidirectional access/share checks. Windows handles carry monotonic generations; stale or foreign grants cannot address a newly reused file slot. Independent positions belong to grants, while file size and unflushed changes belong to the shared object.

The current bounds are 128 simultaneous file identities, 32 grants per process, 2,048 dirty data pages across the Windows group and at most 256 administrative pages. Objects, dirty-page directories and data pages are allocated on demand and released after their final grant. Removing the old permanently allocated 2,048-pointer writer array saves 16 KiB of private metadata per process before the small grant-record changes. These bounds are implementation limits, not total OS memory measurements.

CreateFileW now supports selected regular-file creation dispositions and read/write/delete sharing. Existing files can be edited without first copying their entire contents into RAM. FlushFileBuffers publishes real native COW/CRC data; close of a writable grant also flushes. A normal process exit attempts to flush its open grants and reports a failure, while faults/cancellation discard remaining uncommitted state when the final grant disappears. Truncation/regrowth preserves zero-filled gaps. Pending deletion waits for final close; live-file rename preserves open object identity and requested leaf case. Replacement of an already-open destination and directory moves containing open descendants are refused rather than misdirecting existing grants. General mapped/asynchronous/device file operations, handle inheritance and custom security descriptors are not implemented by this foundation.

The [native shared-file probe](../../evidence/M14/3/development/files-native.json) runs a real Windows parent and child, verifies both-direction sharing conflicts, visibility of unflushed edits, independent positions, stale handles, sparse edits, truncation/regrowth, pending deletion and case-only live rename. Twenty repeated parent/child tasks retain zero managed pages after initialization. Saved bytes are checked independently after the guest stops and again after an independent disk-only start. [Compact installation/startup](../../evidence/M14/3/development/compact-files-candidate.json) and the [original 7-Zip lifecycle with all 106 payload hashes](../../evidence/M14/3/development/original-apps-files-candidate.json) also pass. This remains a development foundation: byte-range locks, durable registry, environment inheritance and complete M14.3 release qualification remain open.

The following canonical-source development build, `9b5c932108e74bb91a97e3bc3fb3f59b`, adds bounded byte-range locks (16 per live file object), synchronous blocking acquisition and exact-owner/range unlock. Waiting threads use an indefinite scheduler state; unlock/close revisits pending requests, with no polling worker or compatibility timer for the lock itself. Exclusive ranges deny other grants' reads/writes; shared ranges deny all writes, including the owner's. Closing a grant releases its ranges. Asynchronous/event-based lock completion is refused explicitly. Same-handle overlapping mixed shared/exclusive locks remain a known semantic gap to resolve before final M14.3 qualification.

Its expanded [native file/lock probe](../../evidence/M14/3/development/files-locks-native.json) tests immediate lock conflicts, forbidden second-handle access, shared-lock reads and rejected writes, foreign unlock refusal, a genuinely blocked Windows thread resuming after unlock, and zero-byte I/O. All twenty repeated parent/child/thread tasks report zero retained managed pages and a 312-page group peak within this synthetic workload. Observer wall times and worker quanta are recorded separately from any real CPU-time claim. [Fresh compact setup/independent starts](../../evidence/M14/3/development/compact-files-locks-candidate.json) and the [original 7-Zip lifecycle](../../evidence/M14/3/development/original-apps-files-locks-candidate.json) pass again. The earlier `2813...` development manifest captured CRLF working-tree bytes for three C/include files; the later canonical-source candidate uses the staged LF bytes and preserves the earlier observations rather than relabelling their build identity.

Build `6d2bdc51247118fec122a7f524fdf56c` resolves that mixed-lock gap: a shared range can overlap the same grant's exclusive range, and exact matching unlock releases the exclusive range first. The expanded [native mixed-lock regression](../../evidence/M14/3/development/files-mixed-locks-native.json) passes twenty times with zero retained pages. The preceding gap remains recorded above as historical development status.

## Persistent registry

Writable user preferences are separate from the installed product's machine-registration view. Use the trusted user root for the backing namespace and validate every access, key/value identity and buffer size at the kernel boundary. A request for an unsupported registry view/security/volatile feature must be refused instead of ignored.

Prefer bounded independent key/value records over rewriting a large duplicated hive on every small update. Reuse native CRC and durable COW publication; record identity must be validated even if a name hash is used to keep storage paths short. A hash collision cannot alias another setting. Avoid a permanently loaded full-registry cache and unsolicited idle writes.

Preserve value type and exact data bytes. Size queries and short-buffer results differ from copying a string: queried registry strings are not guaranteed to include a terminator. Enumerate supported children/values with explicit name/data capacities. Generation-checked key grants retain their access masks and refuse stale or foreign handles. Independent disk-only starts must verify acknowledged settings.

## Environment and lifetime

An environment block belongs to its process. Seed implemented defaults, support real lookup/set/delete/expansion, and snapshot the parent's current block when creating a child unless the caller supplies a supported explicit block. A later parent mutation must not alter a running child's variables. Strings exposed by GetEnvironmentStrings require their own owned copy and release route.

Keep environment allocation bounded and lazy. User-selected TEMP, PATH or USERPROFILE values are data; they must never alter kernel authorization. Reuse the existing process/thread lifecycle and blocking locks, then prove fault/cancellation cleanup of every added resource.

## Implemented registry development profile

Build `6d2bdc51247118fec122a7f524fdf56c` adds real persistent HKCU keys and exact typed values, generation-bound kernel key grants, selected query/set/enumerate/create/delete rights, value/key enumeration, deletion and flush. The selected W APIs preserve raw value bytes, including strings stored without a terminator. Query sizes, short buffers, empty/default values, missing values and deleted or stale handles have distinct results. A deleted key remains deleted to its old grants even if its name is immediately recreated.

The protected backing namespace is `/Data/Windows/<principal-id>/Registry/<key-id>`. Truncated SHA-256 names locate records; full trusted user/key/value identities and native CRCs are checked before use, so a locator collision cannot authorize a different setting. Each value has its own bounded COW record instead of a permanently resident full hive. Successful modifications are synchronously published through the existing native volume. RegFlushKey validates the grant; preceding successful writes are already flushed. This is a selected native persistent profile, not Windows hive-format, ACL/WOW64/transaction/security-descriptor or universal power-loss compatibility.

Bounds per user are 64 persisted keys and 128 values, 767 UTF-8 bytes per complete key path, 255 UTF-8 bytes per value name and 2,048 data bytes per value. There are 32 kernel key grants per process and at most 64 shared open key identities across the group. Key objects occupy lazy pages; at most two further request-scratch pages are admitted. A process does not preallocate a full key-name table or full settings database. The historical installed-product registration text remains a separate read-only view; its runtime handles now also carry generations and selected read rights. General writable HKLM installation services and ANSI registry views remain outside this development profile.

The [native registry probe](../../evidence/M14/3/development/registry-native.json) passes case/Unicode keys, exact DWORD/binary/non-terminated string/default bytes, missing/short buffers, rights, stale/deleted/recreated keys, key/value enumeration, oversized/unsupported/malformed requests and unchanged GetLastError behavior. A real Windows child updates a value read through the parent's existing grant. Twenty repeated parent/child tasks retain zero managed pages and peak at 310 group-owned pages in this synthetic workload. A separate read-only Windows PE verifies the saved value after an independent disk-only start. [Fresh compact setup](../../evidence/M14/3/development/compact-registry-candidate.json) and the [original 7-Zip lifecycle](../../evidence/M14/3/development/original-apps-registry-candidate.json) pass on the same candidate. It is process-local and grows lazily from 512 UTF-16 units up to 8,192 units (16 KiB), with at most 64 variables, 255-unit names and 2,047-unit values. At most 32 caller-owned string-block snapshots are admitted per process. The existing CRT initial-environment view receives a real UTF-8 startup snapshot; ordinary Windows environment changes do not rewrite that cached initial CRT view.

CreateProcessW/A captures either the parent's current block or the caller's selected explicit Unicode/UTF-8 block. ## File-owned timestamps and attributes

Build `bf2e677364e330838feb52b05290d8a2` removes the former 36,872-byte metadata database from every private Windows space. Live identities now carry shared timestamps/attributes within their existing bounded object page. Closed user files use independently CRC-checked records under `/Data/Windows/<principal-id>/Files/<file-id>`. Full user/path identities authorize records; truncated hashes only locate them. User metadata is independent of an application's installation directory, so removal does not remove a document's dates or attributes. The native volume format remains unchanged.

Regular-file rename stages the destination metadata before the native data rename, restores the earlier destination metadata if that rename fails, and cleans up the old record after success. This composes existing COW operations; it does not establish general NTFS transactions or universal crash atomicity. Failed storage cleanup is reported. Directory rename is currently refused explicitly; the previous development description of directory handling must not be read as successful closed-directory rename support.

The selected profile implements shared/read-only/hidden/system/archive metadata and attribute-only grants. Metadata-only opens do not participate in data/delete sharing admission. Read-only files refuse new data-write and delete operations, while permitted attribute updates can clear that flag. File information identifies the native entry slot, so two grants and a live rename retain the same identity. Native files without a Windows metadata record have a documented 1980-01-01 fallback date; this profile does not invent their original creation times. Newly created Windows files receive the available native clock time. Native product/install metadata remains a separate bounded profile, rather than giving ordinary apps write access to their installation directory.

The [native metadata probe](../../evidence/M14/3/development/metadata-native.json) passes cross-process dates/attributes, metadata-only sharing, stable live identities, rename and read-only access checks. Twenty repetitions retain zero managed pages. It then restores the original 7-Zip binary, performs original removal/reinstallation, and uses a separate read-only Windows PE after independent startup to verify that the document and its metadata survived. [Compact installation](../../evidence/M14/3/development/compact-metadata-candidate.json), [original application lifecycle](../../evidence/M14/3/development/original-apps-metadata-candidate.json), [shared file/lock](../../evidence/M14/3/development/files-metadata-native.json), [registry](../../evidence/M14/3/development/registry-metadata-native.json) and [environment/temporary-file](../../evidence/M14/3/development/environment-metadata-native.json) regressions pass on the same candidate.

The identical synthetic shared-file probe falls from 324 to 306 peak group-owned pages, with zero retention. Its observer wall-time median rises from 1.344 to 1.898 seconds because durable file metadata now performs additional real COW work. This is a necessary correctness change and an explicit I/O optimization item for M14.15, not a CPU-time or faster-than-Windows result. [Raw observation and tradeoff](../../evidence/M14/3/development/metadata-resource-observation.json). Earlier development records remain immutable.
