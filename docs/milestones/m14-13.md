# M14.13 - Private app device access, driver ownership and acceleration

Status: planned, not started. Revised by owner instruction on 23 November 2026.
This document schedules future implementation; the current task only edits plans.

Mandatory contract: [independent Windows app environments](../architecture/windows-app-environments.md).
No global application registry or shared app dependencies. Two apps needing the
same component receive independent copies.

## Goal and dependencies

Provide required Windows device/driver, GPU/compute, multimedia, input and
virtualization operations over the native Engacer hardware layer, without
turning app dependencies into global shared packages.

## Work to perform

1. Classify native platform drivers, app-private user-mode driver components and
   required foreign privileged driver interfaces. Give each component an owner,
   authority boundary, real device lifetime and implementation/test plan.
2. Store vendor app-specific DLLs, driver binaries, service registrations and
   configuration within their app environment. Do not silently install one
   shared vendor app driver or service to satisfy several application bundles.
3. Define the necessary WDM/WDF/NT-style binary structures, object, request,
   synchronization, memory/DMA, interrupt and lifecycle contracts. File isolation
   alone does not make a privileged driver safe or provide driver compatibility.
4. Mediate real physical devices through the own kernel. Bind clients, requests,
   callbacks, handles, GPU contexts/VRAM and access rights to the owning AppId.
   Hardware remains physical shared infrastructure, not a dependency copied
   into each folder or a reason to reuse another app's executable components.
5. Resolve device exclusivity, conflicting driver expectations, required global
   kernel semantics and privilege transitions explicitly. Required gaps remain
   implementation work; neither a false success nor an undisclosed global
   dependency fallback is permitted.
6. Implement actual graphics/compute/media/print/input/device operations and
   required virtualization interfaces. Discovery and framebuffer output alone
   do not establish acceleration or a foreign driver's successful operation.
7. Make app update/removal tear down only that app's device execution and
   references. Removing A cannot unload a native platform driver needed by B
   or remove B's separately owned vendor components.

## How and why

Separate app dependency ownership from hardware arbitration and kernel trust.
The native OS owns hardware management; each application owns its installed
software and device-client state. Required privileged compatibility must be
implemented and tested as such, not described as an ordinary folder redirect.

## Deliverables

Device/driver ownership and privilege design, supported ABI/request contracts,
real native driver/acceleration implementations, declared physical/virtual
hardware profiles and independent teardown/fault evidence.

## Acceptance and tests

- Original callers perform actual render/compute/media/input/device work on
  declared hardware; measure results rather than only API availability.
- Two apps using the same physical device retain separate software copies and
  attributable contexts. Remove/fault/update A and verify B's real device work.
- Test device removal/reset, timeouts, failed allocations, cancellation,
  stale handles, privilege rejection and native platform-driver protection.
- Demonstrate resource arbitration for simultaneous and exclusive access.
- Explain and track required privileged/global driver-contract blockers;
  do not claim them implemented by namespace isolation.

## Resources and handoff

Measure total device/driver overhead and app-attributable CPU, RAM, VRAM, DMA,
latency, I/O and idle costs; verify reclamation after faults. Do not count a
configured VRAM size as use or hide costs in an OS broker. M14.14 integrates
real capabilities and actionable diagnostics into the desktop.

## Stage closure

Run meaningful contract, original-code, A/B ownership, persistence/failure and
resource tests for actual implemented behavior. Publish exact evidence, current
English manuals, GitHub source and actual website content before advancing.
Preserve historical media. No automatic approval to start this stage is given
by this planning revision.
