# M14.11 - Private runtimes, services and dependency activation

Status: planned, not started. Revised by owner instruction on 23 November 2026.
This document schedules future implementation; the current task only edits plans.

Mandatory contract: [independent Windows app environments](../architecture/windows-app-environments.md).
No global application registry or shared app dependencies. Two apps needing the
same component receive independent copies.

## Goal and dependencies

Make original app-required runtimes and platform components execute within
the owning M14.10 environment. A dependency folder or fake registry version
must not substitute for working activation and component behavior.

## Work to perform

1. Inventory runtime family/version/architecture requirements from manifests,
   managed metadata, configuration and real activation traces. Distinguish
   .NET Framework (including CLR 4 activation) from modern .NET, native C/C++
   runtimes, scripting engines and Java or other app-required runtimes.
2. Implement required CLR hosting/activation, assembly/fusion binding and
   private framework/GAC/servicing views. Resolve the original runtime's own
   Windows API, file, registry and component dependencies without global reuse.
3. Implement private COM/OLE/WinRT registration and activation, including
   local/out-of-process servers and correct AppId inheritance through brokers.
4. Implement owner-scoped service instances, SCM behavior, RPC/IPC, pipes,
   helper programs, scripts and command environments. Same service/component
   names in two apps must not bind to the same app-owned running instance.
5. Provide the required networking, TLS/cryptography, authentication, data and
   identity semantics. External services and licensing are genuine integration
   requirements; their failure is not automatically a missing local runtime.
6. Add version-aware transitive dependency resolution and activation verification:
   identify required/optional features, conflicts, architecture mismatches and
   cycles. Another independently installed app cannot satisfy this graph.
7. Emit bounded evidence for late runtime/COM/service/helper failures. Separate
   missing components from corrupted installations, access errors, unavailable
   OS contracts and ordinary optional probes. Carry AppId through every event.
8. Start dependencies on demand where their semantics permit; honor explicitly
   authorized background services without starting all installed runtimes at boot.

## How and why

Install and activate private copies using real runtime/platform contracts.
Copying .NET files or reporting Installed in a registry key cannot execute
managed code. A service is an execution lifecycle, not merely a private file.
Version-specific behavior is compared with declared Windows references.

## Deliverables

Native runtime/component/service providers, per-app activation and instance
ownership, dependency graph resolver, attributable failure records and measured
native runtime/helper tasks. Record unsupported required contracts as work.

## Acceptance and tests

- Two apps needing the same runtime have separate installed copies, assembly
  state and service/helper instances; removing one leaves the other's real
  runtime work functional after reboot.
- Exercise different runtime versions, mixed native/managed code, x86 helpers,
  out-of-process COM, restarts, configuration and correct failure propagation.
- Test a dependency first requested by a feature after the main window opens.
- An optional feature probe must not produce a compulsory install prompt.
- Verify failures do not fabricate installed status or corrupt the existing graph.
- Separate runtime computation, framework availability and full GUI/application
  functionality; later UI/device dependencies remain explicit tracked work.

## Resources and handoff

Measure private runtime code/data, activation latency, service idle CPU,
per-app cache bounds, file/device I/O and release after the last actual user.
Do not introduce a global runtime cache or scanner. M14.12 uses real providers
and verification tasks to manage installation and maintenance.

## Stage closure

Run meaningful contract, original-code, A/B ownership, persistence/failure and
resource tests for actual implemented behavior. Publish exact evidence, current
English manuals, GitHub source and actual website content before advancing.
Preserve historical media. No automatic approval to start this stage is given
by this planning revision.
