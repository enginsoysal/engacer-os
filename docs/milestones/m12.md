# M12 — coherent desktop experience

Authorized on 16 November 2026. Execute **M12.0 through M12.18 strictly in order**.
The owner approved this complete sequence and autonomous implementation. Agent
review of the design is authorized; no new user approval is inferred as a gate.
The native scope of each stage and its publication must close before the next
implementation starts. M11.6 remains the qualified download until a newer native
stage has its own exact-source/media qualification. M12.0 is design, not a new OS.

## Ordered implementation and acceptance

### M12.0 — Inventory and design contract

**Deliver:** A complete surface inventory, interaction/state contract and original concept screens.

**How and why:** Reuse proven M11 mechanisms while exposing missing or inconsistent experiences.

**Acceptance:** Check every owner requirement, source-backed inventory, state coverage, original concept rendering and English publication.

**Dependency:** Owner authorization and immutable M11.6 baseline. Close the five publication gates before the next stage.

### M12.1 — Shared visual components

**Deliver:** Semantic typography, spacing, colors, buttons, fields, lists, scrollbars and focus states.

**How and why:** Shared drawing and hit-testing rules prevent each screen drifting into a different interface.

**Acceptance:** Native light/dark component states, text fit, focus, actual scaling and retained-memory/idle measurements.

**Dependency:** M12.0. Close the five publication gates before the next stage.

### M12.2 — Icon system

**Deliver:** Original app, action, folder, file-type and device icons across shell surfaces.

**How and why:** Recognizable silhouettes replace ambiguous letter badges; bounded shared assets avoid per-window duplication.

**Acceptance:** All shipped app identities at small/large scales, themes, missing-icon fallback and cache bounds.

**Dependency:** M12.1. Close the five publication gates before the next stage.

### M12.3 — Desktop and shortcuts

**Deliver:** Consistent desktop layout, icon labels, alignment, selection, background menu and Recycle Bin.

**How and why:** Keep user objects and built-in launchers predictable and independently removable.

**Acceptance:** Select/open/marquee/rename/pin/recycle routes, persistence, overflow and protected core services.

**Dependency:** M12.2. Close the five publication gates before the next stage.

### M12.4 — Windows and title bars

**Deliver:** Consistent app identity, active/inactive chrome, caption controls, borders and reachable window grips.

**How and why:** Preserve proven signed clipping and owner/focus semantics while refining presentation.

**Acceptance:** Move/resize/minimize/maximize/restore/close, inactive state, dirty-close review, keyboard and screen bounds.

**Dependency:** M12.3. Close the five publication gates before the next stage.

### M12.5 — One Files environment

**Deliver:** A common frame and real history for native folders, drives and USB, with Back/Forward/Up and address/sidebar navigation.

**How and why:** The provider changes capabilities, never the basic navigation model.

**Acceptance:** Documents to USB to a directory to Back/Forward/Home, no-device state, detach and truthful title/path updates.

**Dependency:** M12.4. Close the five publication gates before the next stage.

M12.5 delivery passes M12-STAGE5-VM-v1 with its matching public media and
[complete publication proof](../../evidence/M12/5/publication-results.json).
The release tests its named virtual scope; final regression remains M12.18.

### M12.6 — File presentation

**Deliver:** Readable details/icons, columns, sorting, selection, full-name tips and actual provider metadata.

**How and why:** Make content scannable without inventing timestamps or expanding filesystem limits cosmetically.

**Acceptance:** Long supported names, sort stability, narrow windows, selection identity, metadata truth and saved view.

**Dependency:** M12.5. Close the five publication gates before the next stage.

M12.6 delivery passes M12-STAGE6-VM-v1 with matching public media and
[complete publication proof](../../evidence/M12/6/publication-results.json).
Final controller/application regression remains M12.18.

### M12.7 — File commands and transfers

**Deliver:** Consistent toolbar/context commands, transfer feedback, cancellation, conflicts and supported Undo.

**How and why:** Reuse checked storage transactions and preserve sources across interruption.

**Acceptance:** Native and USB copy/move/refusal, protected locations, partial completion, cancellation and independent stored bytes.

**Dependency:** M12.6. Close the five publication gates before the next stage.

**Acceptance:** Open/save/cancel from supported apps, owner modality, extension filtering, conflicts and missing destinations.

### M12.10 — Taskbar

**Deliver:** Consistent app icons, running/active/minimized states, bounded window grouping and context actions.

**How and why:** A launcher and its running windows should have coherent identity without ambiguous duplicate buttons.

**Acceptance:** Multiple windows, minimize/restore/group actions, overflow, pin ordering and optional app removal.

**Dependency:** M12.9. Close the five publication gates before the next stage.

### M12.11 — Multitasking

**Deliver:** Refined switcher and discoverable snap choices/assist within actual window and display limits.

**How and why:** Build on working M11 geometry rather than replacing its tested state machine.

**Acceptance:** Mouse/keyboard snap, preview/cancel, normal-bounds restoration, switching, minimum sizes and quota refusal.

**Dependency:** M12.10. Close the five publication gates before the next stage.

### M12.12 — System tray and quick settings

**Deliver:** Clock/calendar, device status, safe removal and controls backed by real providers.

**How and why:** Expose useful everyday system actions while keeping unsupported hardware functions explicit.

**Acceptance:** Real network/audio/device state, unavailable reasons, safe remove, keyboard navigation and bounded updates.

**Dependency:** M12.11. Close the five publication gates before the next stage.

### M12.13 — Settings and personalization

**Deliver:** A consistent settings hierarchy, previews, persisted preferences and explicit default restoration.

**How and why:** Theme/profile data must customize presentation without bypassing safety or coupling optional apps to the base.

**Acceptance:** Apply/cancel/reset, independent startup, malformed settings refusal and removable-app independence.

**Dependency:** M12.12. Close the five publication gates before the next stage.

### M12.14 — Feedback and errors

**Deliver:** Shared empty/loading/success/refusal/error states, useful notifications and owner-scoped reviews.

**How and why:** Explain what happened and the next useful action without interrupting unrelated work.

**Acceptance:** Missing USB, failed saves/transfers, notification bounds, actionable recovery and preserved work.

**Dependency:** M12.13. Close the five publication gates before the next stage.

### M12.15 — Installer and first use

**Deliver:** Apply shared components and terminology across eight steps, recovery and the first installed desktop.

**How and why:** Maintain the proven destructive-consent and actual installed-boot contracts while improving consistency.

**Acceptance:** Every setup step, Back/cancel, disk/partition operations, write failure, recovery and real reset/detached startup.

**Dependency:** M12.14. Close the five publication gates before the next stage.

### M12.16 — Accessibility

**Deliver:** Keyboard-complete routes, visible focus, contrast, text/display scaling, reduced motion and semantic control identities.

**How and why:** Accessibility participates from M12.1; this stage qualifies it across complete tasks.

**Acceptance:** Keyboard-only tasks, focus order, light/dark/high-contrast, supported scales and reduced motion. Screen-reader support requires its own working protocol/reader.

**Dependency:** M12.15. Close the five publication gates before the next stage.

### M12.17 — Motion and performance

**Deliver:** Direct feedback and bounded optional transitions, shared caches and measured CPU/RAM behavior.

**How and why:** Keep the native lightweight compositor; decoration must not impose continuous work or large per-window surfaces.

**Acceptance:** Peak/retained memory, event/paint observations, idle CPU halt, interrupted transitions and pixel-correct ordinary/HiDPI/4K motion.

**Dependency:** M12.16. Close the five publication gates before the next stage.

### M12.18 — Final qualification and publication

**Deliver:** One frozen final ISO/starter, complete task regression, release assets and fresh website/manual verification.

**How and why:** Stage passes cannot qualify different final bytes or broaden hardware/Windows compatibility.

**Acceptance:** Final native desktop/setup/USB/error/memory tests, all named controller profiles, original 7-Zip MSI lifecycle, exact source/assets and public readback.

**Dependency:** M12.17. Close the five publication gates before the next stage.

## Shared completion rules

Use [the design contract](../architecture/desktop-m12.md), [surface inventory](../architecture/m12-inventory.md),
[user-task guide](../handbook/desktop-m12.md) and [machine-readable progress](m12-progress.json).
Every native stage needs an isolated scoped release, matching ISO/VMware media,
reproducible source identity and task evidence. The design-only M12.0 delivery
publishes its specification/concepts without rebuilding the accepted OS.
Do not redraw a disabled feature as a functioning one. Reuse M11 behavior already
proved; new appearance never implies a larger window quota or a new filesystem.

Review clarity, convenience, friendliness, graphical quality and readability
for every ordinary, empty, busy, failure and recovery state. Automated agent
scenario review is not a human study. Actual novice studies require participants.
Record actual physical framebuffers at ordinary, 150% and 3840x2160, plus bounded
retained/peak memory, idle paints and halted CPUs. Keep failures as diagnostics.
Source, diagrams and controls use English; user-facing progress can be Dutch.

## Publication after each stage

Update architecture/how-and-why, user instructions, tests, scoped release and
progress together; push the canonical repository and verify the resulting
BrixCanvas articles. Update the native homepage explicitly, keep tested downloads
separate from design progress, and verify the index/manual/download links fresh.
Later hardware and Windows expansion remain separate work.
