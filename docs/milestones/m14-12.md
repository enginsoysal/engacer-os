# M14.12 - Owner-bound installation, dependency setup and maintenance

Status: planned, not started. Revised by owner instruction on 23 November 2026.
This document schedules future implementation; the current task only edits plans.

Mandatory contract: [independent Windows app environments](../architecture/windows-app-environments.md).
No global application registry or shared app dependencies. Two apps needing the
same component receive independent copies.

## Goal and dependencies

General original installer execution and dependency lifecycle management inside
the private environment, using M14.10 ownership and M14.11 activation. Keep the
ordinary standalone installation path convenient and primary.

## Work to perform

1. Execute real MSI/MSP, EXE bootstrappers, MSIX/AppX and required custom actions,
   prerequisites, servicing and helper chains. Package semantics are general;
   application-name/digest allowlists are not the final compatibility model.
2. Ordinary installation creates a new AppId and standalone bundle. A separately
   opened installer exposes Install as dependency only in collapsed Advanced
   options, with explicit existing-app selection and target confirmation.
3. Accept owner-bound requests from automatic assistance and right-click Add
   dependency. Preserve the selected AppId through nested setup, downloads,
   helper/elevation brokers, services and restart/resume. Never infer permission
   solely from the most recently running or installed app.
4. Resolve dependency graphs, exact version/architecture constraints, sources,
   required features, disk cost, cycles and conflicts before mutation. Run each
   dependency's actual installer in the chosen environment, not another app's.
5. Track installed files, hives, assemblies, services, cached repair sources and
   external shell references by owner. Source downloads can be inputs; runtime
   operation may not depend on an external download or another bundle's cache.
6. Implement staging, journals, commit, verification, cancellation, rollback,
   repair, update, interrupted-operation recovery and safe uninstall. Private
   transactions live under the app root with preflight space bounds.
7. Handle active processes, authorized background services and reboot-required
   changes explicitly. Do not restart an app with unsaved work automatically.
8. Implement conservative legacy migration: move only attributable state or
   reinstall original sources. Raw directory deletion must leave no required
   dependency broken in other apps; reconcile stale launch references safely.

## How and why

All three UI routes create the same reviewed transaction with an explicit
owner. Kernel authority and installer context are distinct from the visible
installer name. Verification includes actual activation, not only exit code,
file presence or a version registry value. Private copies remove cross-app
dependency reference counting; within one app the graph still controls removal.

## Deliverables

General package/lifecycle services, dependency request/target APIs, durable
per-app inventory and recovery, migration behavior and tested lifecycle flows.
M14.14 supplies the polished desktop frontend on these same APIs.

## Acceptance and tests

- Install A, start it, encounter a late runtime request, download a component
  and explicitly install it for A; verify the feature now really works.
- Open that installer independently: the primary path is still standalone
  installation. Advanced targeting and context-menu targeting both work for
  known and unrecognized dependency installers.
- A nested installer, delayed download, restart or concurrent App B activity
  must not change the target. Removed targets/stale tickets fail clearly.
- Interrupt install, repair, update and uninstall at durable transitions; recover
  the owner without changing B's copied runtime, hives or documents.
- Verify private x86/x64 prerequisites and original custom-action side effects.
- Delete/update A and independently start/use B, including its dependencies.
- Existing M14.8 release/evidence stay immutable; migration has separate proof.

## Resources and handoff

Measure duplicate installed footprint, temporary/rollback peak disk usage,
verification CPU, actual read/write/flush counts and bounded journal/graph data.
No shared dependency store, global app registry or hidden global package repair
cache. Next: device mediation and final user-facing dependency workflows.

## Stage closure

Run meaningful contract, original-code, A/B ownership, persistence/failure and
resource tests for actual implemented behavior. Publish exact evidence, current
English manuals, GitHub source and actual website content before advancing.
Preserve historical media. No automatic approval to start this stage is given
by this planning revision.
