# M16 - Win16 and MS-DOS applications in private environments

Status: planned, not started. Management architecture revised 23 November 2026.
No Win16/DOS execution feature is implemented by this documentation update.

## Scope and architectural decision

Reuse the [independent app environment](../architecture/windows-app-environments.md)
for packaging, dependency ownership, setup, removal and desktop management.
Win16 and DOS are distinct execution/API/device contracts, not smaller PE32+
programs. Inventory 16-bit Windows/NE, DOS MZ/COM and required DOS-extender cases
separately, including any associated 32-bit protected-mode components.

## Ordered work

1. Freeze the formats, x86 execution modes, segmented memory, calling/interrupt
   conventions, Win16 APIs, DOS/BIOS calls, file semantics and hardware behavior
   needed by original software. Build controlled reference probes/corpora.
2. Choose and document the execution technique on x64 Engacer: direct execution
   only where architectural support permits; an own interpreter/emulator or
   other controlled execution mechanism where required. Do not promise native
   execution in an unsupported CPU mode or hide a bundled Windows guest.
3. Implement Win16 task/message/resource/module behavior and required older
   libraries, initialization/configuration and Win16/DOS interactions.
4. Implement needed DOS process/memory/interrupt/file/console behavior,
   per-app drive letters/current directories, short filenames/code pages,
   private INI/configuration/startup files and required extender interfaces.
5. Implement actual required display/input/audio/timing/device behavior through
   the native hardware mediator. A BIOS/port access request cannot be granted
   raw access to unrelated host resources or another app's state.
6. Put each program's libraries, DOS support components, helpers, configuration,
   writable working state and approved disk images inside its own directory.
   Do not invent a registry for software that uses files; when a registry-like
   Windows facility is required, keep the appropriate state private as well.
7. Reuse automatic detection where evidence exists, right-click Add dependency
   and ordinary installer Advanced targeting. Offer program import/setup for
   software without a modern installer; show the intended app owner clearly.
8. Validate original setup/run/use/save/close/repair/remove and cold-start
   behavior, then measure mode/emulation cost and release matching media/docs.

## How and why

One user experience can manage several execution families while retaining
their true semantics. MS-DOS is not an 8-bit Windows generation. Historic
8/4/2/1-bit machines are separate platforms and are not silently included as
additional Windows application milestones.

## Acceptance

- A and B using the same historical library/support program have private copies;
  deleting/updating A leaves B's actual original workload and saved documents intact.
- Test per-app drive/configuration isolation, later-loaded libraries and
  extender dependencies, architecture errors and all three dependency routes.
- Verify actual rendering, input, audio and timing where required, plus crash/
  interrupt containment, bounded resources, restart persistence and safe teardown.
- Measure interpreter/emulation overhead explicitly when used. Do not label
  emulated foreign-mode execution as demonstrated native execution.
- Regress M14/x64 and M15/x86 and publish precise format/workload/hardware scope,
  source/provenance, original results and matching artifacts/website guides.

Outputs: execution decision and contract matrix, native compatibility/device
implementation, original-program corpus, ownership/stability/resource evidence
and current user documentation. Planning does not qualify any legacy program.
