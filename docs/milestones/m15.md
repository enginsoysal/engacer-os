# M15 - Standalone Windows x86 applications in private environments

Status: planned, not started. Management architecture revised 23 November 2026.
This is an umbrella implementation plan; no M15 code or media is built here.

## Scope and dependency on M14

Expand standalone 32-bit Windows applications using the same
[independent app-environment contract](../architecture/windows-app-environments.md).
Necessary x86 installers/helpers of x64 products already belong to M14.10;
M15 must not be used to defer those M14 dependencies.

## Ordered work

1. Inventory PE32 imports, x86 calling conventions, structures, exceptions,
   TLS, pointer width, runtime families and Windows-version behavior. Freeze
   native/reference probes and architecture-correct dependency graph records.
2. Complete standalone x86 loading, execution, process/thread/memory/file/
   registry and error behavior. Add remaining 32-bit NT/API/COM/runtime/service
   semantics on the own kernel; do not equate an x64 DLL with an x86 dependency.
3. Apply AppId/user ownership to all x86 objects, private filesystem/registry
   views, loader caches and app-owned physical code backing. Preserve correct
   WOW64-facing paths/views when x86 and x64 components coexist in one bundle.
4. Install private original prerequisites/runtimes/helpers, including managed,
   native and mixed-architecture chains. Resolve transitive versions, activation,
   services and device needs without another app's copy or a global framework.
5. Reuse all three management routes: automatic evidence-based assistance,
   right-click Add dependency, and ordinary installer Advanced targeting.
   Ordinary standalone installation remains primary.
6. Complete original install/start/use/update/repair/remove, interruption,
   migration and restart scenarios across diverse original x86 applications.
7. Measure CPU, private/retained RAM, total system cost, duplicated disk space,
   I/O, latency and idle behavior. Qualify exact media and publish matching
   source, scope, English guides and actual website content.

## How and why

Reuse the management model, not an incorrect assumption that x64 and x86
execution contracts are identical. Independent dependency versions must be
preserved even where both binaries have the same filename.

## Acceptance

- Two standalone x86 apps needing the same runtime have separate installed
  copies, hives and attributable execution; remove/update A and cold-start/use B.
- Test x86/x64 helper transitions without cross-app dependency reuse.
- Verify static and late requests, optional-probe suppression, all three
  installation routes, crash containment, user documents and actual device/UI work.
- Regress the qualified x64 corpus; x86 support must not break M14 behavior.
- Finite corpus results remain scoped; original tasks and measured performance
  are mandatory before compatibility claims.

Outputs: x86 contract/corpus, native implementation and lifecycle/resource
evidence, exact release artifacts and current documentation. M16 adds different
Win16/DOS execution behavior while retaining this same ownership policy.
