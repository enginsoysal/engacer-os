## Ordered stages

### M14.0 - Original targets and baseline

**Deliver:** Pin original packages, inspect installer/payload/custom-action architectures, inventory static dependencies and native gaps, and freeze functional/performance protocols.

**How and why:** Read-only PE/MSI analysis and exact source references avoid guessing from an x64 download label. Do not execute downloaded apps on the development host.

**Acceptance:** Version/hash inventory, installation-chain decisions, per-app task corpus, bounded performance protocol, source/native baseline, honest unknowns and complete public research delivery.

### M14.1 - Win64 loader and DLL environment

**Deliver:** Extend checked PE32+ mapping, relocations, imports/forwarders/delay imports, module lifetime and dependencies.

**How and why:** Replace the current fixed eight-module/eight-MiB assumptions with explicit tested per-process quotas and demand-backed mappings, not unbounded allocations.

**Acceptance:** Original selected binaries load correctly with access violations, invalid images and missing required functions refused clearly; no GUI compatibility claim from loading alone.

### M14.2 - Processes, threads and exceptions

**Complete within its recorded scope.** [Stage record](m14-2.md), [execution contract](../architecture/runtime-m142.md). M14.2 is an accepted historical native/public delivery.

**Deliver:** Provide real Windows thread/TLS/wait/timer/exception behavior and child-process lifetime over isolated native processes.

**How and why:** The existing one-thread console profile cannot safely substitute fake synchronization or success stubs for real behavior.

**Acceptance:** Concurrent original tasks and child processes behave correctly; faults/cancellation remain contained; repeated close releases owned resources.

### M14.3 - Files, paths and persistent settings

**Complete within M14-STAGE3-VM-v1.** Native tests pass for Unicode paths/search, shared files and synchronous byte locks, durable registry/restart, inherited environments/temporary files and file-owned metadata surviving application removal. Full lifetime and exact VMware regressions also pass; complete public delivery also passes. [Stage record](m14-3.md), [implementation and evidence](../architecture/files-m143.md). [Publication receipt](../../evidence/M14/3/publication-results.json): 555 pages, 359 exact-source articles, 4,063 links, zero known broken targets and 12 explicitly unverified external references.

**Deliver:** Expand Unicode/case/path/share/delete/locking semantics, temporary files, environment and registry behavior.

**How and why:** Translate Windows expectations to native storage with explicit access grants; keep user data separate from product ownership.

**Acceptance:** Selected app preferences/files survive independent starts; conflicting access and missing/denied paths return correct errors without corrupting data.

### M14.4 - Original Windows windows and messages

**Deliver:** Implement the required USER32 window/message/focus/input model and connect it to the native compositor.

**How and why:** Run original application code and its actual message loop rather than recreate the target app as a native lookalike.

**Acceptance:** Original app windows visibly respond to input, focus, move/resize/minimize/close; ownership and modality do not operate the wrong app.

### M14.5 - Drawing, text and common controls

**Deliver:** Implement required GDI/text/resources/menu/control/dialog behavior for the pinned applications.

**How and why:** Share native drawing/fonts where semantics match, with bounded surfaces and dirty-region repaint; provider/name presence is not semantic compatibility.

**Acceptance:** Readable working original app interfaces at ordinary and named HiDPI profiles, with pixel and behavior evidence; no vendor GPU/DirectX claim.

### M14.6 - Open, save and clipboard interoperability

**Deliver:** Connect original app file dialogs, clipboard and actual document access with Files.

**How and why:** Preserve requesting-window ownership and file semantics; original app data must be checked independently.

**Acceptance:** Open/edit/save/reopen, Unicode names, cancel and cross-app text clipboard tasks pass without lost or misdirected data.

### M14.7 - Reusable MSI execution

**Deliver:** Implement the selected packages' actual MSI standard actions, conditions/properties/component lifecycle, rollback and required custom actions.

**How and why:** Replace the current one-digest console adapter with reusable behavior. Notepad++ MSI requires a real x64 WiX custom-action DLL and cmd/xcopy semantics; never skip it to claim successful installation.

**Acceptance:** Selected original MSI packages install/remove/reinstall correctly, including conditions, cancellation and fault recovery; missing mandatory actions refuse clearly.

### M14.8 - Original x64 EXE installers

**Deliver:** Execute pinned original AMD64 installer code, its GUI and required helpers/uninstaller.

**How and why:** SumatraPDF provides a measured x64 route. The measured Notepad++ x64-labelled EXE is x86 and explicitly waits for M15; its original x64 MSI remains an M14 target.

**Acceptance:** At least one complete original x64 EXE installer chain and original MSI chains work; all required child binaries are inventoried and exercised.

## Program-wide gates

App identity, installer architecture, payload architecture, helper architecture and required runtime behavior are separate records. Never call an x86 setup compatible because its product contains x64 code. Required unsupported operations fail honestly. Static import coverage is neither behavior coverage nor a compatibility percentage. Original downloads remain outside OneDrive and outside public source unless deliberately reviewed for distribution.

No app/version/task is supported until its exact original bytes pass the full registered task. All three initial mandatory target profiles remain requirements unless the owner explicitly revises them. Optional app removal must not break Files, Settings, the desktop or other apps. Preserve physical memory bounds, per-process isolation, checked I/O, readable errors and normal graphical installation paths.

M15 expands x86 Windows app and mixed-architecture installer chains. M16 expands actual Win16 and the required DOS execution/device/API routes, with extenders inventoried separately. 8/4/2/1-bit historical machines are not additional Windows application architectures; separate emulation may be considered later.
