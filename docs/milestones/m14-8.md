# M14.8 - Original x64 EXE installers

In development after completed M14.7 native and public delivery. M14.7 remains the qualified download; no M14.8 image or original Sumatra installer is qualified yet.

## Exact target

Use unchanged `SumatraPDF-3.6.1-64-install.exe`: 11075960 bytes, SHA-256 `1eee71cccd2ea6e94d5bcea54ee2f759844da3e1a0ee2f6045035b1d17b94381`, AMD64/PE32+, static TLS and exception metadata. The x64-labelled Notepad++ EXE is x86 and remains M15; retain its qualified original x64 MSI.

## Ordered implementation

1. Inspect matching vendor 3.6.1 source and actual required installer/payload/helper architectures and hashes. Keep optional shell integration separate.
2. Run a labelled native startup diagnostic in an owned clone. Record original bytes, kernel/source identity and the first actual missing API or fault. Private dispatch instrumentation is diagnostic, not shipped-route qualification.
3. Implement required ABI, resources, controls, messages, files, registry, processes and runtime behavior against primary contracts. Required unsupported behavior refuses; original bodies remain unchanged.
4. Add ordinary source selection, review, confirmation and original EXE launch, binding file hash, arguments, destination and scoped authority.
5. Complete original GUI installation, required helpers, original removal and reinstall. Independently inspect actual files, shortcuts, registry and personal data after disk-only starts.
6. Freeze full M14.8 media; retain M14.7 MSI/runtime/desktop regressions, add this original chain and resource checks, and test actual VMware startup. Close English docs, GitHub downloads and the actual website before M14.9.

## Why

An EXE installer authors its own behavior. The original program performs installation through accurate OS APIs; manually unpacking payloads, replacing its body or embedding Windows cannot qualify it. Diagnose measured failures before adding speculative APIs. Keep allocations and writes bounded; configured RAM is not measured task or total OS use.

The original GUI and required child/uninstall chain are mandatory. Silent or extract-only modes can support diagnostics but cannot replace GUI acceptance. Check flags and payload names against 3.6.1 rather than applying newer documentation blindly.

## Development observation: original startup

The unchanged original installer reached native execution on the accepted M14.7
kernel through a private diagnostic dispatcher, then refused at
`USER32.dll!RegisterWindowMessageW("TaskbarCreated")` (original return RVA
`0x2f91`). The private dispatcher is not a shipped installer route. Its original
failure and disassembly are preserved in `evidence/M14/8/development/`.

The M14.8 implementation adds a separate, lazily allocated session message
namespace. It survives process exit and is not deletable through global atom
APIs. Repeated registration does not increase a reference count. Numeric-looking
names are strings, not integer atoms. The bounded profile currently admits 64
names in one 4096-byte page with 1854 UTF-16 storage units and names up to 255
units; exhaustion returns an error without modifying existing registrations.
ASCII spelling folds case; other Unicode scalars compare exactly, so complete
Windows linguistic case folding is not qualified. Only the measured wide API is
implemented here; the ANSI API remains unsupported rather than pretending an
arbitrary encoding works. Kernel traps serialize access on the assigned Windows
execution processor. A host contract test covers duplicate overflow, independent
atom deletion, supplementary Unicode, invalid input and both capacity limits.
The full development build `87d34bba6ce1108cde8ee0032d2f8a85` passes actual
installation, two no-ISO startups and zero retained Settings task pages in the
128-MiB configured guest profile. Its private original-installer startup passes
the first registered-message call and next refuses `IsDBCSLeadByte` at return
RVA `0x3043`. Five pages remain after cleanup versus four in the earlier probe:
one is the intentionally retained session message table. Native cross-process
identity and original installation are not yet qualified. These are development
observations, not milestone acceptance.

The selected ACP/OEM profile is UTF-8. It has no Windows DBCS lead-byte ranges;
Windows-1252 likewise has none. The new lead-byte APIs therefore report false
for every byte in supported encodings, preserve last error on valid negative
answers, and explicitly refuse unsupported code pages in the extended API. A
host test calls the actual production codec implementation across all 256 byte
values and checks its reported CPINFO ranges. This does not add East Asian DBCS
conversion support. [Microsoft contract](https://learn.microsoft.com/en-us/windows/win32/api/winnls/nf-winnls-isdbcsleadbyteex).

Primary contract: [Microsoft RegisterWindowMessageW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerwindowmessagew).
