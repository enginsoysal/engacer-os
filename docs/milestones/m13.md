## Ordered stages

**Deliver:** Original installation, disk, desktop, Start, Files and Settings concepts; shared design tokens; source-backed M12.18 gap inventory; complete ordered M13 plan; task-first website navigation and a search interaction prototype/specification.

**How / why:** Compare accepted native captures and implementation with the complete user journeys. Preserve working M12 mechanisms. Separate current instructions from chronological project history; put ordering and current-release identity in a central Git-tracked index. Inspect BrixCanvas capabilities before selecting the production search implementation.

**Acceptance:** Every gap maps to a later stage. Concepts are clearly design-only, include ordinary and HiDPI layout rules and do not claim native implementation. Current documentation is organized by reader task; history remains reachable in natural numeric order. Publish actual homepage, articles and matching design evidence, verify public source links, downloads, search behavior and responsive layouts. Any unimplemented overlay remains explicitly pending, with an implementation path rather than a false pass.

## Common product and publication gates

- Clarity, convenience, friendliness, graphical quality and readability are separate review fields; passing automated control activation alone does not pass them.
- Review normal, empty, hover, focus, selected, disabled, busy and error states; mouse/keyboard; compact/ordinary/HiDPI; light/dark/high contrast. Long names and larger text remain readable.
- Normal installation, app launch, folder navigation and settings need no terminal/external instructions. Remove unnecessary decisions/clicks, never destructive consent.
- Reference profiles: 2 vCPU/512 MiB at 1920x1080; 2 vCPU/1 GiB at actual 3840x2160. Separately disclose 128-MiB/compact capability checks and firmware-specific refusals. Guest RAM is not OS usage. Record framebuffer/cache cost separately from fixed state and retained allocations. No polling at idle; bounded queues/caches and zero unexplained completed-task retention.
- Fixed/peak budget deltas must be recorded against M12.18 before each change; a second 4K framebuffer cannot be described as a few bytes of shell state. Hardware acceleration remains a separate capability.
- Close each stage with appropriate evidence, English architecture/user docs/status, GitHub push, a visible scoped release (design-only prerelease for M13.0), native Brix homepage Save and fresh public documentation/download/source/search/mobile/link checks before proceeding. Never advance only because code was committed.
- Keep large fixtures outside OneDrive. Preserve historical accepted artifacts. This request does not authorize bypassing cleanup policy rejections or deleting source.

## Whole tasks and evidence classes

First boot -> install -> two disk-only starts; default/customized/used-disk/cancel/error; launch/pin/switch/recover; create/rename/navigate/copy USB/delete/restore; customize/cancel/reset; remove Calculator without breaking the base. Each task records result, actual image/source, user-visible feedback and independent data when relevant.

Automated native tests, agent visual review, owner feedback and a consented novice pilot are different evidence classes. A proposed formative pilot has at least six inexperienced younger/older participants, appropriate guardian arrangements if children participate, predefined safe tasks, assistance/error counts and a >=90% unaided task-completion target. That small sample is feedback, not universal statistical proof. No recruitment or messaging is authorized by this plan.

The full website target is part of [M13.0's portal contract](../architecture/website-m13.md): task routes, current/history separation, ordered Previous/Next, mobile navigation and same-page accessible search. Platform-dependent implementation is explicitly tracked; a prototype cannot pass a production-overlay gate.
