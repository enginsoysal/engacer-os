# M14.10 - Private execution, files, registry and process ownership

Status: in progress. The owner authorized M14.10 implementation.

The initial kernel change scopes named synchronization objects and mappings to
a key derived from the canonical product root and user in the kernel launch
request. The hosted mapping regression exercises same-app visibility, separate
backing for another scope, and independent cleanup. This is an initial lookup
boundary. The kernel now stores the canonical product GUID separately from the
physical path and derives the object owner from the GUID and account. Children
inherit both fields from the parent kernel space. Durable registration, generation and generation binding, private registry and loader
views, mixed-architecture execution, and native acceptance remain open.

The [compact QEMU smoke test](../../evidence/M14/10/compact-boot-smoke.json)
passed on the initial candidate from commit 9566a568. It installed on a virtual
disk at 128 MiB and booted twice without ISO media. This checks installation
and desktop boot; the app isolation acceptance tests below are still pending.

The process-ownership candidate from commit b3b33478 passed the
[compact QEMU installation and two disk boots](../../evidence/M14/10/compact-process-owner-smoke.json)
and [VMware Workstation UEFI boot to the installer](../../evidence/M14/10/vmware-installer-boot.json).
The [hosted process query test](../../tests/m14/process1410_scope_host.py)
exercises the production lookup with same-owner and foreign-owner processes.
These results leave the native two-app ownership and mixed-architecture cases open.

The MSI path grant permits catalog enumeration and committed product records.
Foreign pending transactions can be checked for existence, with file opens and
image probes denied. Foreign DLLs, cached MSI sources and other payloads are
also denied. That keeps related-product conflict checks working
with the existing transaction format. A brokered metadata-only query is still
needed to remove direct access to these legacy records.
The [hosted path test](../../tests/m14/path1410_scope_host.c) checks own-product
access, read-only catalog access, foreign payload denial and traversal rejection.
The earlier catalog-boundary build, before the pending-transaction content
restriction, passed 1,029 hosted original MSI file-staging checks and
295 hosted terminal-cleanup checks. On build eeea44b55767cd28cd80adad42a0b12c,
the [128 MiB QEMU install and disk-boot regression](../../evidence/M14/10/compact-catalog-smoke.json)
passed, as did [VMware Workstation UEFI boot to the installer](../../evidence/M14/10/vmware-catalog-boot.json).
The [original x64 Notepad++ MSI regression](../../evidence/M14/10/original-msi-catalog-regression.json)
also passed native installation, removal and reinstallation on that build.




Mandatory contract: [independent Windows app environments](../architecture/windows-app-environments.md).
No global application registry or shared app dependencies. Two apps needing the
same component receive independent copies.

## Goal and dependencies

Implement the M14.9 identity and namespace contracts on the own kernel while
retaining real Windows-visible loader, NT object, file and process semantics.
This foundation is required before installing dependencies into app environments.

## Work to perform

1. Attach immutable AppId/user/architecture/generation context to processes,
   threads, file/registry handles, memory objects and installer brokers. Inherit
   it across child creation, exceptions, cancellation and authorized privilege
   transitions; never trust a caller-editable environment variable as authority.
2. Implement private filesystem views for program/system/data/temp names.
   Resolve traversal, links, aliases, case, Unicode, locking and metadata inside
   the grant. Explicit external document grants do not grant foreign app roots.
3. Implement per-app durable registry machine/class/user stores, WOW64 views,
   enumeration, notifications, permissions and accurate errors. Project OS
   facts explicitly; do not use a global mutable Windows hive as a fallback.
4. Bind PE imports, delay/runtime DLL loads, manifests, activation contexts,
   API-set/system-module views and module caches to the correct environment.
   Loaded app components cannot come from a different AppId's backing pages.
5. Provide real process/thread/TLS/exception/wait/memory/identity behavior and
   owner-scoped named objects. Preserve original error and cleanup semantics;
   a namespace wrapper cannot turn unsupported work into successful no-ops.
6. Implement necessary x86 installer/helper execution and x64/x86 transitions
   for x64 products now. Respect 32-bit System32/SysWOW64 and registry views;
   standalone x86 product expansion remains M15.
7. Add bounded terminal-failure events at actual import/activation/helper
   boundaries. Record architecture, requested identity, final error and owner.
   Do not classify every failed intermediate search as a missing dependency.
8. Implement protected bundle metadata and minimal rebuildable native indexes;
   enforce owner-safe rename/move and stale-object rejection.

## How and why

Enforce ownership at native object/dispatch boundaries, then expose compatible
Windows paths and structures. API semantics still require implementation.
Physical independence prevents uninstall of A from invalidating B; correct
context propagation prevents nested setup or services escaping that ownership.

## Deliverables

Native context/namespace/handle contracts and implementations, private hive and
loader routing, required mixed-architecture support, failure-event interface,
migration groundwork and exact-source tests. No per-app Windows guest VM.

## Acceptance and tests

- A and B install identical-named DLLs at identical Windows-visible paths and
  registry keys; both execute correctly with different private bytes/values.
- Inspect backing identity, link counts/module caches and private mappings;
  different displayed paths alone are insufficient evidence of independence.
- A cannot load B's DLL, read/write B's hive, forge a child owner, exploit a
  stale handle, escape through a link or connect to B's named object by accident.
- Exercise deferred DLL loading after successful launch and preserve true errors.
- Verify real x86 child execution, architecture-correct binding and cleanup.
- Update/delete A, cold-start B and verify B's actual operation and durable state.
- Retain the existing native process/file/runtime regressions on new frozen media.

## Resources and next stage

Measure context/lookup overhead, physical private pages, handle/event bounds,
fixed-state growth, idle cost and retained allocations. No cross-app memory
coalescing as an optimization. M14.11 consumes the native ownership foundation.

## Stage closure

Run meaningful contract, original-code, A/B ownership, persistence/failure and
resource tests for actual implemented behavior. Publish exact evidence, current
English manuals, GitHub source and actual website content before advancing.
Preserve historical media. No automatic approval to start this stage is given
by this planning revision.
