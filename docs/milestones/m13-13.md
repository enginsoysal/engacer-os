# M13.13 - Blocking stability qualification and release

Status: planned, release-blocking. Added 18 November 2026 after the owner reported frequent freezes on M13.8. M13.9 retains its scoped motion/recovery work; M13.12 tests integration. The owner subsequently requested comprehensive stability work at this final milestone while continuing the ordered sequence. Hardware expansion waits for this stability gate.

## Scope and purpose

This stage qualifies stability on one frozen candidate. It adds no desktop redesign, standard app or hardware feature. Current M13.8 media are testing-only with known freeze reports. Their historical scoped task passes do not establish stability. Preserve the exact M13.7 visual-freeze evidence and every failed subsequent candidate.

## Real-duration acceptance

Run at least eight real hours on a fresh instance of the exact enabled-device VMware package, including at least two uninterrupted idle hours and repeated active/idle cycles for the rest of the workday. Include folder navigation, selection, context menus, dragging/resizing, scrolling, Start/search, Settings preview/cancel/apply, saved documents and unsaved edits. Record the actual elapsed time and observation gaps. Accelerated timer-boundary tests are separate and never substitute for elapsed time.

Verify visible response as well as input, clock and presentation progress. A matching serial app-launch event with an unchanged image fails. Test the normal graphics path and a labelled injected timeout/recovery path; distinguish simulation from a naturally occurring fault. Repeat supported screensaver activation/wake and disabled behavior, retaining documents/windows and consuming wake gestures safely.

Use actual named reference resolutions and constrained-memory profiles. Verify fixed state, framebuffer/shadow cost, managed peak and retained memory separately; completed tasks must have no unexplained retention, and idle operation must not introduce polling. Reopen exact saved bytes after independent starts with the ISO disconnected, retaining ordinary firmware discovery. Keep user VMs and host configuration untouched.

## Failure policy and release

Any unexpected hang, stalled visible response, crash, restart, lost input or corrupted/lost data blocks release. Retain the failed report and media/source identity, diagnose and correct the cause, freeze new bytes and repeat the complete required run. A watchdog or automatic restart cannot turn a failure into a pass. A partial or deliberately interrupted run is diagnostic only.

M13.12 whole-product integration must pass first. Then publish the exact candidate, truthful tested limits, English manuals, GitHub evidence and downloads, actual native BrixCanvas Saves and fresh complete public website checks. A named VM workday pass is not a promise of universal hardware compatibility or a human usability study. Only then does hardware recognition become the next development priority.
