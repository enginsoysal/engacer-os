# M14.14 - Desktop dependency workflows and original application interfaces

Status: planned, not started. Revised by owner instruction on 23 November 2026.
This document schedules future implementation; the current task only edits plans.

Mandatory contract: [independent Windows app environments](../architecture/windows-app-environments.md).
No global application registry or shared app dependencies. Two apps needing the
same component receive independent copies.

## Goal and dependencies

Deliver the three convenient dependency routes over M14.10-M14.13 mechanisms
while preserving the original app interface and the Engacer desktop. A design
mockup is not acceptance of the native user flow.

## Work to perform

1. Keep ordinary Open installer / Install app as the primary/default action.
   Put Install as dependency for an existing app in collapsed Advanced options.
   Even a recognized runtime installer must not silently replace this default.
2. Add right-click Add dependency to app launchers and installed-app management.
   Bind the actual AppId, display its name/location and let the user choose
   a source. Preserve keyboard access, focus, navigation and clear cancellation.
3. Implement automatic assistance only for attributable necessary dependency
   failures. Inspect static declarations and actual loader/runtime/component/
   helper events, including requests after successful app launch. No continuous
   disk/process scanner and no modal prompt for every failed optional probe.
4. Present the requested component, runtime family/version/architecture,
   requesting app, evidence, source, installed/temporary disk cost and exact
   intended action before consent. Do not promise a package fixes an unknown
   error; offer diagnostics/manual selection when confidence is insufficient.
5. Implement Advanced target selection with searchable app names and distinct
   identities for duplicates. Recent requests may be suggestions inside that
   workflow; no selection based solely on last foreground app.
6. Make all three routes converge on one transaction and progress/cancel/
   retry/recovery view. Distinguish missing, incompatible, installed and
   verified components. Restart the original app only with appropriate consent.
7. Provide per-app dependency details, diagnostics and version/update/removal
   controls without exposing helpers as unrelated default desktop clutter.
8. Complete needed Windows controls, fonts, DPI, international input,
   accessibility, COM shell integration, shortcuts, associations, clipboard,
   printing and Open/Save interactions with correct owner/message semantics.

## How and why

Automatic detection is evidence-based assistance, not omniscience. The manual
routes remain available for an app's private error message or an unrecognized
installer. The main UI stays simple for inexperienced users; advanced targeting
is explicit. Ordinary native kernel event boundaries provide the needed evidence.

## Deliverables

Native accessible desktop workflows, per-app dependency inventory/diagnostics,
readable original application integration, actual screenshots/interaction
receipts and current English tutorials clearly matching shipped capabilities.

## Acceptance and tests

- Exercise all three routes end to end with the same dependency and confirm
  identical ownership, actual activation, persistence and cleanup.
- Standalone installation remains first/default; Advanced starts collapsed.
  Unknown installers can still be deliberately added to the chosen app.
- A late .NET requirement is attributed to A while B is active. Optional DLL
  searches, permissions and network errors do not trigger false compulsory setup.
- Test duplicate app names, renamed/removed targets, delayed downloads, expiry,
  offline sources, keyboard-only use, Back/Cancel and interrupted repair.
- Confirm no automatic restart loses user work and original errors remain
  available when a proposed fix fails.
- Inspect ordinary/compact/HiDPI physical rendering, focus, hit targets,
  clipping and readable text. Label agent review separately from user studies.

## Resources and handoff

Measure notification/event bounds, lookup/painting cost, input-to-visible
latency and idle behavior. No periodic dependency scanner or blanket service
startup. M14.15 validates the integrated flows under realistic composition.

## Stage closure

Run meaningful contract, original-code, A/B ownership, persistence/failure and
resource tests for actual implemented behavior. Publish exact evidence, current
English manuals, GitHub source and actual website content before advancing.
Preserve historical media. No automatic approval to start this stage is given
by this planning revision.
